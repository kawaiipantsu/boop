# Publishing a Boop release

Everything in this directory except this file is generated by `make dist` and
is **not** committed — `dist/` is in `.gitignore`. Rebuild rather than reuse.

---

## 1. Choosing a tag

Semantic versioning, `v` prefix, annotated tags only (PROJECT.md §33).

| Situation | Tag | Notes |
|:--|:--|:--|
| Testing before a real release | `v0.1.0-rc.1` | Increment the `rc` number for each attempt |
| First usable release | `v0.1.0` | Cut when milestones 0–7 are stable (§68) |
| Bug fixes only | `v0.1.1` | No new behaviour |
| New features, backwards compatible | `v0.2.0` | Pre-1.0, so minor bumps carry breaking changes too |
| First stable API commitment | `v1.0.0` | Only when the config schema and tool contracts are settled |

Pre-1.0, the minor version carries breaking changes; that is normal and
expected while `0.x`. Say so in the release notes rather than pretending
otherwise.

**Release candidates** must be marked as pre-release on GitHub. A tag containing
a hyphen (`-rc.1`, `-beta.2`) sorts *before* the plain version under semver, so
`v0.1.0-rc.1` correctly precedes `v0.1.0`.

## 2. Cutting the release

```bash
git switch develop
git switch -c release/0.1.0-rc.1

# Move the entries under [Unreleased] into a new version section in
# CHANGELOG.md, dated today. The Makefile reads the version from the first
# "## [x.y.z]" heading, so this step sets the version for everything else.

make release-check        # clean tree, changelog entry, tag free, no blocking TODOs
make dist                 # six targets + checksums.txt

git commit -am "chore: prepare v0.1.0-rc.1"
git switch main && git merge --no-ff release/0.1.0-rc.1
git tag -a v0.1.0-rc.1 -m "Boop v0.1.0-rc.1"
git switch develop && git merge --no-ff release/0.1.0-rc.1
git branch -d release/0.1.0-rc.1

git push origin main develop
git push origin v0.1.0-rc.1
```

For a release candidate the release-branch dance is optional — tagging
`develop` directly is fine, since an RC is not release history. Do use it for a
real release.

## 3. Creating the GitHub release

When pushing a `v*` tag to GitHub, the `.github/workflows/release.yml` workflow automatically builds all platform distribution archives, generates `checksums.txt`, extracts the corresponding section from `CHANGELOG.md`, and creates the GitHub Release (marked as pre-release when the tag contains a hyphen like `-rc.1`).

Alternatively, releases can still be created manually with the GitHub CLI:

```bash
gh release create v0.1.0-rc.1 \
  --title "Boop v0.1.0-rc.1" \
  --notes-file dist/notes.md \
  --prerelease \
  dist/*.tar.gz dist/*.zip dist/checksums.txt
```

Drop `--prerelease` for a real release. **Always upload `checksums.txt`** — the
installer verifies against it and warns loudly when it is missing.

### What to write in the release description

Write for someone deciding whether to upgrade, not for someone reading a
commit log. Structure that works:

````markdown
One or two sentences on what this release is for.

## Highlights

- 🏠 The three or four things a reader actually cares about
- 🔐 Lead with anything affecting safety or data
- 🐛 Then notable fixes

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/kawaiipantsu/boop/main/install.sh | sh
```

Or download a binary below. Verify it:

```bash
sha256sum -c checksums.txt --ignore-missing
```

## Known limitations

- Be specific and honest here. This section earns more trust than the
  highlights do.

## Full changelog

https://github.com/kawaiipantsu/boop/compare/v0.0.9...v0.1.0-rc.1
````

Rules that keep the notes worth reading:

- **Copy the "Known limitations" section from `CHANGELOG.md` verbatim.** A user
  who discovers a limitation themselves trusts the next release note less.
- **Name what is unverified.** The Lemonade and LM Studio adapters were written
  against inferred endpoints; every release note should keep saying so until
  someone tests them against real servers.
- Do not list every commit. Link the compare view instead.
- No marketing language. "Faster" needs a number or it should not appear.
- If a release changes the config schema or a default, that goes at the top
  under its own **Breaking changes** heading, with the migration.

## 4. Artifacts

| File | Platform |
|:--|:--|
| `boop_<version>_linux_amd64.tar.gz` | Linux x86-64 |
| `boop_<version>_linux_arm64.tar.gz` | Linux ARM64 |
| `boop_<version>_darwin_amd64.tar.gz` | macOS Intel |
| `boop_<version>_darwin_arm64.tar.gz` | macOS Apple Silicon |
| `boop_<version>_windows_amd64.zip` | Windows x86-64 |
| `boop_<version>_windows_arm64.zip` | Windows ARM64 |
| `checksums.txt` | SHA-256 for all of the above |

All binaries are static, built with `CGO_ENABLED=0`, and have no runtime
dependencies. macOS builds are unsigned, so Gatekeeper will quarantine a
downloaded binary; users need `xattr -d com.apple.quarantine ./boop`. Mention
that in the notes for any release macOS users will see.

---

## 5. After publishing

```bash
# The installer resolves "latest" from the GitHub API. A pre-release is not
# "latest", so verify against an explicit version.
BOOP_VERSION=v0.1.0-rc.1 BOOP_INSTALL=/tmp/booptest \
  sh -c 'curl -fsSL https://raw.githubusercontent.com/kawaiipantsu/boop/main/install.sh | sh'
/tmp/booptest/boop version
```

Then bump `CHANGELOG.md` with a fresh `## [Unreleased]` section so the next
change has somewhere to go.
